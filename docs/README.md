# Observatory documentation map

The code, accepted ADRs and candidate-bound evidence describe the implemented Observatory. The
original numbered product documents remain useful design context, but they do not override a newer
implementation boundary or measured result.

## Source-of-truth order

1. Executable code, schemas, tests and checked fixtures.
2. Accepted architecture decisions in `adr/`.
3. Present-tense architecture in `architecture/`.
4. Candidate-bound records in `release-evidence/` and `model-tools/verification/`.
5. Current implementation handover in `implementation/`.
6. Original product, experience and research documents `00`–`10`.

An old plan can explain why a feature was considered, but it cannot promote an unavailable
instrument, browser or release criterion. Only the named evidence profile can do that.

## Current implementation set

- `architecture/` explains package boundaries, runtime flow, replay integrity and static release.
- `implementation/00-five-phase-plan.md` records the delivery sequence.
- `implementation/05-session-05-handover.md` records the completed Phase 5 source and local gates.
- `implementation/06-post-phase-5-review.md` is the post-candidate engineering review: split
  evidence, remaining launch blockers and owner decisions.
- `deployment/static-release.md` is the host-neutral build, smoke and rollback runbook.
- `../release-evidence/` contains the 78-criterion ledger, manifest, protocols and generated
  decision.
- `../model-tools/` contains the independent model/runtime verification boundary.

## Maintaining documentation

Update user guidance when controls, labels, privacy or local-storage behaviour changes. Update the
architecture map and an ADR when a durable boundary changes. Update the current handover with exact
observed commands and limitations; never copy a planned result into it. Generated evidence files
must be regenerated by their owning script rather than hand-edited.
